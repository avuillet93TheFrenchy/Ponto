# Tauri v2 Capability Configuration

Resolve the project profile first (`.claude/PROJECT-CONTEXT.md`): `<tauri>` is the Tauri folder (usually `src-tauri`). If `stack.tauri` is false, stop: this skill is Tauri-only. Read the `conventions` files for the scopes the app legitimately needs.

In Tauri v2, the frontend can only call a backend command or plugin API if a capability explicitly grants it. There is no global allow-list. This is a hard break from Tauri v1.

Authoritative sources used in this skill:

- [Tauri v2 — Capabilities](https://v2.tauri.app/security/capabilities/)
- [Tauri v2 — Capability reference (ACL)](https://v2.tauri.app/reference/acl/capability/)
- [Tauri v2 — Permissions](https://v2.tauri.app/security/permissions/)
- [Tauri v2 — File System scope](https://v2.tauri.app/plugin/file-system/)

## When to use

- The user adds a new Tauri command or plugin and the frontend cannot call it
- Console shows: `command not allowed`, `permission denied`, or `Not allowed to call command`
- The user wants to audit which permissions are granted
- A new window label is added and its capability is missing

## File location

Capabilities live in `<tauri>/capabilities/`. Each file is either JSON or TOML. Tauri auto-discovers every file in this folder. Source: [Tauri Capabilities — file format](https://v2.tauri.app/security/capabilities/).

## Minimal valid capability (JSON)

```json
{
    "$schema": "../gen/schemas/desktop-schema.json",
    "identifier": "main-capability",
    "description": "Capability for the main window",
    "windows": ["main"],
    "permissions": ["core:default"]
}
```

Required fields per the [Capability reference](https://v2.tauri.app/reference/acl/capability/):

- `identifier` — unique name for this capability
- `windows` (or `webviews`) — labels this applies to
- `permissions` — list of permission identifiers

Optional but recommended:

- `$schema` — enables IDE autocomplete; the schema is generated by `tauri-build` into `<tauri>/gen/schemas/`
- `description` — human-readable purpose
- `platforms` — limit to e.g. `["windows", "linux", "macOS"]`; defaults to all
- `local` — `true` (default) means apply to local app URLs
- `remote.urls` — array of remote origins permitted to use these permissions (use with caution)

## Permission identifier syntax

Form: `${plugin-name}:${permission-name}`

Examples (from official plugin docs):

- `core:default` — sane defaults for core APIs
- `fs:default`, `fs:allow-read-text-file`, `fs:allow-write-text-file`
- `dialog:default`, `dialog:allow-open`, `dialog:allow-save`
- `shell:default`, `shell:allow-execute`
- `notification:default`
- `event:default`, `window:default`, `app:default`

For commands defined in your own `<tauri>` crate, only `${permission-name}` is required (no plugin prefix). Tauri auto-generates `allow-<cmd>` and `deny-<cmd>` per command listed in the build script's `COMMANDS` const.

## Scoped permissions (object form)

To narrow what a permission can access, use the object form:

```json
{
    "$schema": "../gen/schemas/desktop-schema.json",
    "identifier": "main-capability",
    "windows": ["main"],
    "permissions": [
        "core:default",
        {
            "identifier": "fs:allow-write-text-file",
            "allow": [{ "path": "$APPDATA/*" }]
        },
        {
            "identifier": "fs:scope",
            "allow": [{ "path": "$APPDATA" }, { "path": "$APPDATA/**/*" }]
        }
    ]
}
```

Scope path variables (from [File System plugin docs](https://v2.tauri.app/plugin/file-system/)) include `$APPDATA`, `$APPCONFIG`, `$APPCACHE`, `$APPLOCALDATA`, `$AUDIO`, `$CACHE`, `$CONFIG`, `$DATA`, `$DESKTOP`, `$DOCUMENT`, `$DOWNLOAD`, `$EXE`, `$FONT`, `$HOME`, `$LOCALDATA`, `$LOG`, `$PICTURE`, `$PUBLIC`, `$RESOURCE`, `$RUNTIME`, `$TEMP`, `$TEMPLATE`, `$VIDEO`. Verify the current list in the linked doc before relying on a variable.

`deny` rules can also be supplied and always take precedence over `allow`.

## Multi-window patterns

Separate the capability per window label, especially when privileges differ:

```json
{
    "identifier": "settings-capability",
    "description": "Settings window — limited access",
    "windows": ["settings"],
    "permissions": ["core:default", "dialog:allow-open"]
}
```

The main window's capability should not include the settings window in `windows` if they need different permissions. Security boundaries are derived from window labels, not titles (source: [Capabilities doc](https://v2.tauri.app/security/capabilities/)).

## Audit workflow

When asked to audit:

1. Read every file under `<tauri>/capabilities/`
2. Build a table: `capability identifier | windows | permissions count | broad permissions present (yes/no)`
3. Flag any of:
    - `shell:allow-execute` without a scope constraint
    - `fs:allow-write-*` with scope `**` or `$HOME/**`
    - `http:default` or `http:allow-*` with overly broad `urls` scope
    - `remote.urls` containing wildcards or non-HTTPS origins
    - Capabilities targeting a window label not declared in `tauri.conf.json`
4. Suggest narrower scopes where applicable

## Common error: command exists but cannot be called

When a Rust command in `#[tauri::command]` is callable from the codebase but not from the frontend:

1. Confirm the command name is registered in `tauri::Builder::default().invoke_handler(tauri::generate_handler![...])`
2. Confirm there is a permission for it. If the command is `read_config`, Tauri generates `allow-read-config`. Add it to the relevant capability:
    ```json
    "permissions": ["allow-read-config"]
    ```
3. Confirm the capability applies to the window label calling `invoke()`

## Report back

After creating or modifying capabilities, summarize:

- File path created/modified
- Identifier and target windows
- Permissions added (and any scope constraints)
- Any broad permissions the user should review

Do not invent permission identifiers. If unsure whether `${plugin}:${permission}` exists, check `<tauri>/gen/schemas/desktop-schema.json` (auto-generated by `tauri-build`) or the plugin's permissions reference page.
